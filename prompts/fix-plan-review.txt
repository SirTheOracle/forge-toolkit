You are executing the 'fix-plan-review' stage of a forge fix-pipeline.

Slug: {slug}

Follow the fix-plan-reviewer skill at ~/.claude/skills/fix-plan-reviewer/SKILL.md

This is a SINGLE-AGENT adversarial review of the fix plan. You are not a teammate-spawning skill — you read the artifacts and write the review yourself.

You do NOT re-investigate the bug. You do NOT propose fixes for issues you find — that is the revise mode of adversarial-fix-plan, which only runs if you raise BLOCKING items.

Inputs (READ ALL BEFORE REVIEWING):
- .dev/proposals/{slug}/diagnosis.md (the accepted root-cause report; treat as ground truth)
- .dev/proposals/{slug}/fix-plan.md (the canonical plan to review)

Optional cross-references if you need to validate a synthesis choice:
- .dev/proposals/{slug}/fix-plan-A.md (surgical proposal, pre-synthesis)
- .dev/proposals/{slug}/fix-plan-B.md (robust proposal, pre-synthesis)
- .dev/proposals/{slug}/fix-synthesis.md
- .dev/proposals/{slug}/fix-reconciliation-notes.md

Attack the plan from these angles. Be specific — vague feedback is useless. For every issue, cite the fix-plan.md section + line/anchor:

1. **Cause coverage** — does every diagnosed cause in diagnosis.md map to at least one Change row in the plan's Coverage Matrix? Any orphaned causes? Any "EXPLICITLY DEFERRED" rows whose rationale is weak?
2. **Defense adequacy** — are the regression-prevention measures load-bearing for the bug class? Or are they cosmetic (e.g., a test that only exercises the happy path)?
3. **Scope correctness** — does the plan touch files OUTSIDE the diagnosed-cause set? If yes, are those touches strictly necessary, or scope creep? Conversely, does the plan UNDER-cover (skips a file the diagnosis pointed at)?
4. **Regression risk** — does any Change row plausibly break adjacent functionality? Cite specific call sites or shared-helper consumers that could see behavior changes.
5. **Rollback integrity** — is the rollback story honest? Can it actually be reverted cleanly given the change set, or are there hidden migrations / data-shape changes?
6. **Test plan integrity** — do the tests actually exercise the failure mode from the diagnosis? Or do they test peripheral concerns? Are any tests self-validating (assert example against itself)?
7. **Risk honesty** — does the Risk section hand-wave, or does it name concrete failure modes? Anything the plan glosses over that you'd lose sleep about?

Output: write your review to `.dev/proposals/{slug}/fix-review.md` BEFORE sending FORGE_DONE. The FORGE_DONE callback must be a one-line summary only; the digest agent reads the report file from disk.

The fix-review.md MUST contain:
- A 1-paragraph summary of your overall verdict (approve / approve-with-notes / revise required / reject)
- A bulleted list of issues, each rated `CRITICAL` / `MAJOR` / `MINOR` / `ADVISORY` with the rubric:
  - CRITICAL — plan will not fix the bug or will break unrelated code; do not advance
  - MAJOR — plan will likely fix the bug but has a real defect (missing defense, weak rollback, scope creep)
  - MINOR — plan is sound but could be tightened (clarity, test naming, etc.)
  - ADVISORY — observation, not a request
- For each issue: cite the fix-plan.md section, state the problem, state what specifically would need to change for you to clear it. Do NOT propose the fix yourself — describe the gap.
- A 1-line `BLOCKING_ITEMS` count = number of CRITICAL + MAJOR (these block advancement)
- End with three lines, exactly:
  CONFIDENCE: HIGH/MEDIUM/LOW
  BLOCKING_ITEMS: N
  NOT_COVERED: <one line per axis / surface / entry path you did NOT exercise, or NONE with a justification>

CONFIDENCE rubric: "If I cleared this plan as-is, would the resulting fix actually resolve the diagnosed bug without regression?" If yes → HIGH (typically with 0 CRITICAL + 0 MAJOR). If you have concerns but the plan is mostly sound → MEDIUM. If the plan is fundamentally off → LOW.

When complete:
  ~/bin/forge-bridge callback --slug {slug} --stage {stage} --worker {worker} --status DONE --quiet \
    --message "see .dev/proposals/{slug}/fix-review.md"

If blocked (artifact missing, can't read something):
  ~/bin/forge-bridge callback --slug {slug} --stage {stage} --worker {worker} --status BLOCKED --quiet \
    --message "{issue}"

Hard rules for this stage:
- Read-only on source code. You verify fix-plan.md claims against the codebase, but do NOT modify source files.
- Do NOT propose alternative fixes. Your job is to identify gaps in the plan, not to design a competing plan.
- Do NOT silently rubber-stamp. If the plan is genuinely sound, your CONFIDENCE: HIGH and BLOCKING_ITEMS: 0 is a real signal — earn it by attacking from every angle in the list above.
- Do NOT type /clear yourself — the orchestrator drives clear (codex panes don't need clear anyway).
