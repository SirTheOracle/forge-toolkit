You are executing the 'fix-scout' stage — the read-only ROUTING stage that runs BEFORE any forge fix-pipeline. You group one service's triaged QA issues by shared root cause and assign each group a fix tier. You do NOT fix, do NOT write code, and do NOT run the full diagnosis (the per-group fix-investigate stage owns deep diagnosis later). Your job is the routing decision a human will approve.

Slug: {slug}

Inputs (READ ALL FIRST):
- .dev/proposals/{slug}/scout-input.md — the service name and the actionable `forge-fix` issues for it (issue numbers, coded IDs, and full verbatim bodies). The runner wrote this; it is your work-list.
- .claude/forge-project.yml — project layout, services, test commands.
- The codebase (Read tool) — ground every claim in real file:line.
- Prior pipeline artifacts: skim final files (diagnosis.md / fix-plan.md / *-report.md) under any related `.dev/proposals/<slug>*` directories for this feature area. If a section has been worked several times, that history is a signal the cause is subtle — say so.

Investigation checklist (this is the routing analysis, not a full diagnosis):
1. Read every issue body. Extract the DISTINCT failure modes — a single issue title can hide multiple defects (e.g. "code showing AND Day-Of empty" is two causes). Do not trust symptom wording to define a group.
2. Map the implicated subsystem(s): where content is generated, the data schema/shape, and EACH render path (e.g. on-screen vs PDF/exported output are often separate paths that can diverge). Find the specific file:line where each failure mode originates.
3. For EACH issue, classify its root cause(s). Mark multi-cause issues explicitly.
4. Find shared causes across issues (→ cluster) and genuinely distinct causes (→ singleton or split). A cluster means ONE fix resolves all covered issues — shared root cause, NOT shared service or shared symptom wording.
5. Size each group: `quick` (bounded — ≤ a couple files, clear cause, local tests) or `full` (murky cause, sprawling, risky, multi-file, or flow-breaking).

Multi-cause / many-to-many rules (do not violate):
- A group's `close_keywords` may list an issue ONLY if the group fixes ALL of that issue's causes. A group that fixes one cause of a multi-cause issue closes nothing on its own — do not claim otherwise.
- Do NOT carve a quick sub-fix out of a multi-cause issue as its own group if that issue also has a full-tier cause; fold the quick sub-fix into the full group that actually closes the issue. (Piecemeal sub-fixes that close nothing are exactly what causes repeated failed passes.)
- Group by coherent subsystem / root-cause area, then list every issue the group must FULLY resolve. Use `drop_conditions` for issues whose dominant cause is uncertain until the fix-investigate stage clarifies it.
- Cross-service: if you suspect a root cause spanning multiple services, set CROSS_SERVICE_SUSPECTED: yes, describe it, and do NOT force the issue into a service-local group.

Output — write `.dev/proposals/{slug}/routing-plan.md`. One YAML record per group, each followed by a short prose rationale. Schema per group:
  group_id:                # <service>-<date>-g<N>
  service:                 # e.g. eval
  tier:                    # quick | full
  covered_issue_numbers:   # [68, 69]
  covered_coded_ids:       # [EVAL-012, EVAL-013]
  current_labels:          # snapshot per covered issue (for idempotency/abort)
  root_cause_hypothesis:   # short prose — NON-AUTHORITATIVE routing metadata; the full
                           #   pipeline's A/B investigators must re-derive independently
  confidence:              # high | medium | low + one-line why
  slug:                    # the fix slug this group will run under (no collision with existing .dev/proposals/)
  branch_name:             # fix/<slug>
  close_keywords:          # "Closes #68 #69" — emitted to the PR ONLY after per-issue verification
  required_tests:          # commands the fix must pass (from forge-project.yml)
  drop_conditions:         # when to un-cover an issue from this group
  approval_status: pending

Hard rules for this stage:
- Read-only on source code. Modify NO source files. Your only output is routing-plan.md.
- You do NOT set GitHub labels, open PRs, cut branches, or dispatch fixes — the runner owns all mutations. You produce a plan, nothing else.
- Every root-cause claim cites file:line. Do not assert causes for symbols that don't exist.
- Hypotheses are routing metadata only — never treated as ground truth by downstream stages.
- Do NOT type /clear yourself — the orchestrator drives clear.

End routing-plan.md with exactly five lines:
  CONFIDENCE: HIGH/MEDIUM/LOW
  GROUPS: N
  CROSS_SERVICE_SUSPECTED: yes/no
  BLOCKING_ITEMS: N   (count services you could not route, and any group whose dominant cause you could not identify)
  NOT_COVERED: <one line per axis / surface / entry path you did NOT exercise, or NONE with a justification>

CONFIDENCE rubric: "Could the runner act on this routing plan — set labels, write problem statements, dispatch — without re-scouting?" If yes → HIGH. If the grouping is sound but one or more dominant causes need the fix-investigate stage to confirm → MEDIUM. If the evidence can't yet support a reliable grouping → LOW (and explain what's missing).

When complete:
  ~/bin/forge-bridge callback --slug {slug} --stage {stage} --worker {worker} --status DONE --quiet \
    --message "see .dev/proposals/{slug}/routing-plan.md — N groups"
